## 二、★ 第一个要求：三面板互斥（用户定的 ✓）

### 用户原话

> “板子互斥 ✗ 开启的情况下点击另一个板子就互斥 ✗
>  关掉前一个渲染当前的”✓

### 谁参与 / 谁不参与

| 面板 | 参与互斥？ | 理由 |
|---|---|---|
| 绘画（= 会话） | ✅ | 用户主动打开的工作页面 |
| 设置 | ✅ | 同上 |
| 技能 | ✅ | 同上 |
| 交互面板 | ❌ | ★ 它是 pi 提问时【自动弹出来抢焦点】的 ✗ 若参与 ⇒ 你正读着设置，pi 一问，设置就没了 ✓ |
| 调试板 | ❌ | 开发时的观察窗 ✗ 用户想一直看着 ✓ |
| 自由按钮配置页 | ❌ | 用户：“自由按钮配置页什么鬼？”⇒ 没把它算进“板子”里 ✓ |

### 实现（`src/main.ts` 的 `showExclusive`）

```ts
type ExclusivePanel = "session" | "settings" | "skills";
const showExclusive = (which: ExclusivePanel): void => {
    if (which !== "session") sessionPanel.hide();
    if (which !== "settings") settingsPanel.hide();
    if (which !== "skills") skillsPanel.hide();

    if (which === "session") sessionPanel.show();
    else if (which === "settings") settingsPanel.show();
    else skillsPanel.show();
};
```

★ 所有入口都改走它 ✓：侧栏 ☰ / ⚙ / 技能按钮、命令面板的 showSessions /
showSettings / showSkills ✓

### ★ 一个必须说清的真相：VS Code 的 WebviewPanel 【没有 hide()】

```
想让它消失只有 dispose() ✗
⇒ 代价：切回来时 webview 会【重建】✓
  · 前端重新加载 → 重新握手（sessionReady / settingsReady）→ 重新拉一次数据 ✓
  · 用户看到的是“面板重新出现”✗ 可接受 ✓
★ 另外一个好处：dispose 不丢 lastColumn ✗ 面板会回到用户上次拖去的那一列 ✓
  （lastColumn 存在 Panel 类实例上 ✗ 类实例活得好好的 ✓）
```

### ★ 设置面板里没保存的改动？

```
★ 直接丢 ✗（用户定的：\"直接关，丢弃改动\"✓）
   理由：设置面板是“随手改的地方”✗ 改完记得点保存 ✓
★ 没有做 dirty 上报 / 确认框 ✗ 保持简单 ✓
```

## 三、★ 第二个要求：两个「动作后自动关闭」（用户定的 ✓）

### 用户原话

> “两个配置两个行为 ✗ 这两个行为由配置开关关闭 ✗ 这两个行为就不存在 ✓
>  绘画面板：一旦切换绘画或者点击新建绘画 ✗ 点击完关闭这个面板 ✗
>  技能面板：点击它有两个行为（注入输入框 / 直接发送）✗
>  这两个动作一旦触发就自动关闭这个面板”✓

### 翻译成两个配置

| 配置项 | 默认 | 位置 | 管什么 |
|---|---|---|---|
| `pi-bridge.sessions.closeAfterAction` | **true** | 组「pi-bridge：会话」 | 切换会话 / 新建会话 → 关面板 ✓ |
| `pi-bridge.skills.closeAfterAction` | **true** | 组「pi-bridge：面板：技能」 | 注入输入框 / 直接发送 → 关面板 ✓ |

★ 用户定的：**只加 VS Code 设置** ✗ 不进 pi 的设置面板 UI ✓
　（所以这次**没动** `src/pi/settings-schema.ts` ✓）

### ★ 触发范围（严格按用户说的 ✗ 没有自作主张扩大）

```
会话面板：
  ✅ switchSession  —— 切换会话
  ✅ newSession     —— 新建会话
  ❌ exportSession / importSession / deleteSession / renameSession
     —— 这些是“管理”动作 ✗ 用户没说 ✓ 而且它们本来就会弹原生框 ✓
  ★ 侧栏的「＋ 新建」也发同一个 newSession ✗
    那时面板没开 ⇒ isOpen() 挡住 ✓ 不会误关（也不会有别的副作用 ✓）

技能面板：
  ✅ skillInsert    —— 注入聊天输入框
  ✅ skillAsCommand —— 直接作为命令发送
  ❌ skillOpenFile / skillHide / skillDelete
     —— 右键菜单里的“管理”动作 ✗ 用户还要接着管别的 ✓
```

### ★ 时机：点击即关（不等 RPC 结果）

```
宿主【收到消息就先关】✗ 然后再去 await 真正的工作 ✓
⇒ 代价：切换失败时你已经看不到面板了 ✓
  但侧栏会弹错误提示 + 焦点已经回输入框 ✓ 不至于找不着北 ✓
★ 为什么不做成“成功后关”？
  用户明确选了“点击即关”✗ 而且实际操作上更跟手 ✓
```

### ★ 焦点回聊天输入框

```
两个行为都调 chatView.focusInput() ✓（跟交互面板答完面板一个套路 ✓）
· 会话：新建完本来就要打字发第一条 ✓
· 技能：「注入输入框」→ 焦点当然该在输入框 ✗ 好接着改接着发 ✓
```

## 七、★ 踩坑记录：技能面板「自动关闭」第一版【失效】

### 现象（用户实测报的 ✓）

> “两个行为里面绘画自动关闭实现了 ✗ 但是技能面板的自动关闭没实现 ✗
>  无论是注入还是直接发送 ✗ 都是没有关闭的”✓

### 根因：关闭逻辑加在了【永远不会执行】的分支里

```
技能面板的消息走 SkillsPanel 自己的 onMessage 回调 ✓
  （main.ts 里构造 SkillsPanel 时传的那个闭包 ✓）
【不经过】handleFrontendMessage ✗

而我第一版加在：
      handleFrontendMessage 里的 if (msg.kind === "skillInsert") { … }
  ⇒ 那条分支 B31 之后就已经是【死代码】✗
  ⇒ 关闭逻辑永远不会跑 ✓ 静默失效 ✓
```

### ★★ 为什么会加错？（比 bug 本身更值得记）

```
我 grep "skillInsert" 时看到【宿主里确实有 skillInsert 处理】✓
⇒ 就以为「技能面板 → 宿主」走的就是那条路 ✓
⇒ 实际那是 B25 时代【侧栏技能面板】的老分支 ✗
   B31 把面板搬到编辑器区之后就死了 ✗ 但【没人删】✓

★ 教训：死分支【主动误导】✗ 比“没有”更危险 ✓
  ⇒ 所以这次把它连同消息类型一起删了 ✓ 见下 ✓
```

### 修法

```
① src/main.ts：把 closeSkillsPanelAfterAction() 搬到
   ★ SkillsPanel 自己的回调里 ✗（skillInsert / skillAsCommand 两个分支 ✓）
② 删掉 handleFrontendMessage 里的四个死分支
   （skillDetail / skillInsert / skillToInput / skillAsCommand ✓）
   ★ skillToInput 更彻底：它连【发送方】都没有 ✓
③ src/bridge/format-frontend.ts：把这四个消息类型一并删掉 ✓
   ⇒ 以后谁再想往那边加逻辑 ✗ 编译期就找不到这个 kind ✓
```

### ★ 这个坑暴露的系统性问题

```
编辑器区的面板有【两条不同的路由】✗
  转交型（会话 / 设置 ✗ B35 写的）：回调 → handleFrontendMessage
  自处理型（技能 / 命令 ✗ B31/B32 写的）：回调里自己写 if 链
⇒ 同一件事（“面板发来的消息”）有两个藏身处 ✓
⇒ 加逻辑时只要选错一条 ✗ 就是【静默失效】✓

★ 用户当场指出：“怎么不统一？”✓
★ ⇒ 下轮 B36 就做这个 ✗ 见 [ITERATION](../ITERATION.md) ✓
```
