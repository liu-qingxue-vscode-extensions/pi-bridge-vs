## 二、★ pi 的路径约定（实测 + 源码实证 ✗ 全部可算，不用探测）

### 2.1 环境变量（来自 `pi --help` 的原文）

```
PI_CODING_AGENT_DIR          - Config directory (default: ~/.pi/agent)
PI_CODING_AGENT_SESSION_DIR  - Session storage directory (overridden by --session-dir)
PI_PACKAGE_DIR               - Override package directory (for Nix/Guix store paths)
PI_OFFLINE / PI_TELEMETRY / PI_SHARE_VIEWER_URL  - 其它
```

### 2.2 源码里的精确实现

```ts
// ① 数据目录（唯一的"根"）
getAgentDir() = process.env.PI_CODING_AGENT_DIR ?? join(homedir(), ".pi", "agent")
   ★ ".pi" 来自 pi 包 package.json 的 piConfig.configDir（默认 ".pi"）

// ② 以下全部【硬编码在 agentDir 之下】
<agentDir>/settings.json      ← ★ 设置（用户配的 defaultModel / sessionDir …）
<agentDir>/models.json        ← 模型目录
<agentDir>/auth.json          ← 凭据
<agentDir>/sessions/          ← 会话默认位置
<agentDir>/themes/ tools/ bin/ prompts/ <name>-debug.log

// ③ 会话目录可以单独覆盖
sessions = process.env.PI_CODING_AGENT_SESSION_DIR ?? <agentDir>/sessions
           （--session-dir 参数优先级更高）

// ④ 包目录 & 版本
getPackageDir() = process.env.PI_PACKAGE_DIR ?? 从 __dirname 往上找 package.json
VERSION         = 读 <packageDir>/package.json 的 version

// ⑤ 更新日志
CHANGELOG = <piPackageDir>/CHANGELOG.md      ← 硬路径 ✗ 挂在 pi 包根下
```

### 2.3 ★ 关键结论：读一个死路径就能拿到全部

```
agentDir = PI_CODING_AGENT_DIR ?? ~/.pi/agent      ← 一个值
   ↓ 读 <agentDir>/settings.json（死路径）
   ↓ 取其中的 sessionDir 字段（用户配过才会改）
sessionRoot = --session-dir ?? settings.sessionDir ?? <agentDir>/sessions
   ↓
★ 全部路径都是一条【确定的推导链】✗ 不需要扫描文件系统去"猜" ✓
```

**实测记录**（本机）：

```
~/.pi/agent/settings.json 的键（22 个）：
  lastChangelogVersion, theme, packages, defaultProvider, defaultModel,
  defaultThinkingLevel, enabledModels, compaction, …, sessionDir（schema 支持 ✗ 当前未设）
  ⇒ defaultModel = "deepseek-flash" ✗ defaultProvider = "deepseek" ✓
```

### 2.4 会话目录的语义（★ 用户点出的危险点）

```
pi 的原文：--session-dir = "Directory for session storage and lookup"
   ⇒ 【存和读用的是同一个值】✗ 不是"生成目录"那么简单
   ⇒ 改它 = 同时换了"写去哪"和"去哪找"
   ⇒ 所以会出现数据分裂：新会话写新地方 ✗ 旧会话看不见
★ 因此：这个值【不暴露给用户】✗ 想改的人自己去改环境变量 / settings.json ✓
```

## 三、★ 定位：本体不依赖本体

### 3.1 问题

```
代码里有 3 个值导入（其余全是 import type ✗ 编译后擦除）：
   getAgentDir() / getPackageDir() / VERSION
而 @earendil-works/pi-coding-agent 在 node_modules 里是【手动软链】✗ 不是正式依赖
⇒ 打 vsix 时：8.37MB（含整个 pi SDK ✗ 里面还有 AWS SDK 等用不到的）
```

### 3.2 为什么"把 pi 打包进来"是错的定位

```
① 版本错配：扩展里那份 pi 是【发布时那一版】✗ 永远旧
   ⇒ 用户装的是新版 pi ✗ 而我们 spawn 的是…… 到底哪个？
② 那三个信息全错：
   getPackageDir() 会指向【扩展自己】✗ 不是用户的 pi
   VERSION 也是旧的 ⇒ 版本变化检测失效
③ 体积：8.37MB（90% 用不到）
```

### 3.3 正确关系

```
★ 我们是【前端 UI】✗ pi 是【后端进程】（通过 stdio RPC 通信）
★ 所以 pi 对本扩展的地位 = 【运行前提】✗ 不是【依赖库】

   性质等同：Java 插件要先装 JDK ✗ Python 插件要先装 Python
   ⇒ 前提由用户准备 ✗ 扩展不该把它塞进自己肚子里 ✓
   ⇒ 三个信息【运行时去问】或【按约定算】✓
```

### 3.4 三条路线对比（并存 ✗ 各有场景）

| | 做法 | 代码改动 | 能装 vsix | 说明 |
|---|---|---|---|---|
| A | 链接项目目录 | 无 | ✗ | ★ VSCodium **跳过软链**（实测）|
| B | bundle 成 CJS | 要改 ESM API | ✓ | 8.37MB→199KB（实测 ✗ 但踩了坑）|
| C | 复制目录 / 同步脚本 | 无 | — | 开发循环差一点 ✗ 零风险 |
| D | 把 pi SDK 变正式依赖 | 无 | ✓ | ✗ 8MB ✗ 且定位错（见 3.2）|

## 五、★★ 懒加载分析（用户论证 ✗ 已实测验证）

### 5.1 用户的论证

```
★ 发第一条消息之前 ✗ 【完全不需要子进程】：

   ① 刚打开（没开会话）→ 顶栏显示【默认模型】
      ← settings.json 的 defaultModel / defaultProvider / defaultThinkingLevel ✓

   ② 打开 / 切换会话 → 渲染整个会话（含顶栏模型）
      ← 会话文件里每条 assistant 消息【带 model】✓（实测 712/712 条 ✗ 连 usage 都有）

   ③ 会话列表 ← 扫 sessions 目录（纯文件）

   ⇒ 第一次真正需要子进程 = 【用户发第一条消息】
```

**实测数据**：

```
settings.json:   defaultProvider=deepseek  defaultModel=deepseek-flash  defaultThinkingLevel=high
会话文件:        assistant 消息带 model 字段（712 条全部 ✓）✗ 还有 usage ✓
```

### 5.2 现状为什么"打开就启动"

```
✓ 懒加载机制【完好】（PiClient.ensureStarted ✗ 只在 sendRaw 时触发 ✗ 三重保证）
✗ 但 activate 之后：前端一就绪 → onReady 回调 → 补"模型 / 思考深度" → get_state
   ⇒ sendRaw ⇒ ensureStarted ⇒ 子进程被提前拉起
```

### 5.3 ★★ 会话文件的数据够不够渲染（用户问 ✗ 已实证）

> 用户："理论上是够用的，百分百够用，因为派本体也是拿着绘画文件给你传输一遍而已。"

**实测会话文件的结构**（1516 条记录 ✗ 是个 append-only 事件流）：

```
type = "message"                1498  ← ★ 真正的消息（顶层 message 字段里是 role/content）
type = "custom"                    8     扩展状态（如 mode-guard-state）
type = "custom_message"            4     ★ 扩展插入的消息（有 content / display）
type = "context_edit"               3     上下文编辑（targetId / replacement）
type = "model_change"               1     ★ 模型变化点
type = "thinking_level_change"      1     ★ 思考级别变化
type = "session_info"               1     ★ 会话名（title）
type = "compaction"                 1     ★ 压缩记录（有 summary ✗ 我们 UI 里本来就显示它）
type = "session"                    1     文件头（cwd / version）

★ 每条记录都有 parentId ⇒ 【树结构】⇒ 分叉功能的数据源也在这
★ 消息里的内容块：toolCall 667 / thinking 554 / text 338(assistant) + 112(user)
                 toolResult text 666 / ★ image 3（工具产生的图片也在）
```

**结论：渲染需要的全都在，且比 get_messages 更全**

| 渲染需要 | 数据来源 |
|---|---|
| 正文 / 思考 / 工具调用 / 结果（含 image） | `type=message` |
| 顶栏模型（含切换点） | `model_change` + settings.json 默认值 |
| 会话名 | `session_info` |
| 压缩提示 | `compaction` |
| 分叉 | `parentId` 树 |

```
★ get_messages 返回的是【pi 加工后的消息列表】（跳过事件 ✗ 插入 system/custom）
  而我们读文件拿到的是【原始全量】✗ 加工步骤（事件→消息的筛选）我们本来就要做 ✓
⇒ ★ 所以"打开 + 切会话 + 渲染"可以【完全不启动子进程】✓✓
```

### 5.4 结论

```
★ 顶栏模型名【不该问子进程】✗ 应该：
     无会话 → 读 settings.json 的默认模型
     有会话 → 读会话文件里的 model 字段
★ replaySessionMessages 现在走的是 get_messages（RPC ⇒ 拉起子进程）
   ⇒ 可以改成【直接读会话文件】✗ 顺带：无 RPC 往返 ⇒ 切会话更快 ✓
★ 这才是真正的懒加载 ✗ 用户："我发第一句话，OK，真正的（进程）启动，这才是真正的懒启动"
```

## 六、打包尝试踩的三个坑（已记进代码注释 ✗ 教训留档）

### 坑 1：ESM → CJS 的模块格式切换

```
为 bundle 而把宿主产物从 ESM 改成 CJS（因为 package.json 有 "type": "module" ✗
   .js 会被当 ESM ✗ 而 esbuild 输出 CJS ⇒ "module is not defined"）
★ 切换时要搜的东西（我漏了第一步）：
     import.meta.url / import.meta.resolve    ← ESM 有 ✗ CJS 没有
     __dirname / __filename                   ← CJS 有 ✗ ESM 没有（反向）
     createRequire(import.meta.url)           ← 依赖前者
本项目的两处：
     src/pi/paths.ts          import.meta.resolve(...)
     src/panels/cmd-summary.ts  createRequire(import.meta.url)
```

### 坑 2：VSCodium 的 `.obsolete` 黑名单

```
卸载 vsix 后 ⇒ VSCodium 把 "liu-qingxue.pi-bridge-vs-1.0.0" 写进
   ~/.vscode-oss/extensions/.obsolete
之后建【同名】软链 ⇒ 名字在黑名单 ⇒ 直接跳过（连 package.json 都不读）
⇒ 症状：链接存在 ✗ 但扩展列表里没有它 ✗ 输出面板也没频道
⇒ 修：rm ~/.vscode-oss/extensions/.obsolete
```

### 坑 3：vsce 与软链 / 开发软链

```
node_modules 里的 @earendil-works/pi-coding-agent 是指向全局 pi 的软链
⇒ vsce 会顺着它跑进 pi 的目录做依赖检查 ⇒ 报一堆 extraneous ⇒ 打不了包
（临时挪开也不行：vsce 会先跑 vscode:prepublish ⇒ npm run compile ⇒
  而 compile 需要那个软链做类型检查 ⇒ 死循环）
```
