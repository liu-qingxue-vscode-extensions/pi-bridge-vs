## 二、折叠体系（★ 本轮的核心设计 ✗ 用户画的）

```
┌ 工具渲染器（按 toolName 分派）──────────────┐
│  bash  → 行 = [命令行] + 输出每行            │
│  read  → 行 = 文件内容每行                   │
│  edit  → 行 = patch 每行                     │
│  通用  → [参数块] + 结果文本每行              │
│        ↑ 各自封装 ✗ 上层不知道这些是什么 ✓    │
└──────────────┬──────────────────────────────┘
               │ 上报：行数
               ▼
┌ 折叠器 tool-fold.ts（只有一份）─────────────┐
│  pi-bridge.style.toolFold 规则 → 裁头 N + 尾 M │
│  顶栏那行 = 唯一的折叠按钮（也吃规则）          │
└──────────────────────────────────────────────┘
```

### 规则格式

```jsonc
// VS Code 设置里是【添加项】列表（跟调试板的忽略列表同一体验）
"pi-bridge.style.toolFold": ["bash:1:0", "edit:0:0", "read:2:1", "*:2:1"]
//                            工具名:头行数:尾行数          * = 兜底
//        0:0 = 全折   all = 不折
```

### ★★ 踩坑：分隔符不能用 `;`

```
宿主生成：  --pi-tool-fold: bash:1:0; edit:0:0; read:0:0; …
                              ↑ 分号在 CSS 里是【声明结束符】
⇒ 变量值被截断 ⇒ 只有第一条规则到达前端（后面全丢）
⇒ 症状：① 只有 bash 的规则生效 ② 残缺片段解析失败 → 日志刷"规则看不懂"
⇒ 修：分隔符改【逗号】（CSS 值里合法）
★ 教训：CSS 变量只适合装【标量】✗ 结构化数据要另开消息通道
```

### 其他折叠相关的坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 尾部少一行 | 规则写 `3:3` 只显示 2 行 | 输出末尾有 `\n` ✗ split 多一个空元素 ✗ 去掉末尾换行 |
| read 少一行 | `read:2:1` 只显示头 1 行 | 我给所有工具都减了 1（那是给 bash 命令行预留的）✗ 加 `hasFixed` 参数 |
| 收不起来 | read 的内容没反应 | 内容块忘了加 `.fold-unit` ✗ 且 `.part-text` 不是 fold-unit |
| 机制打架 | 整块被藏掉、内部 peek 白做 | 行级内容**不要**再带 `.fold-unit`（自己管自己）✓ |
| 空框 | 末尾空行变成一个什么都不显示的空框 | 片段 trim 后为空 → 不生成；并去掉 `.code-block` 的 margin（视觉缝合）|
| 整块点击后没法复制 | 一按下就折叠 | 加"位移 > 4px = 拖选不折叠" + "有选中文字不折叠" |

## 三、bash 终端样式

```
┌ 🔧 bash ──────────────────────── ✓ ┐
│ 💬 echo  🟢 node  📝 printf         │  ← 摘要行（命令主体 + 等级色）
│ ~/Projects/pi-bridge-vs ❯ echo …   │  ← 命令行（shiki 上色 ✗ 固定 dark-plus）
│ node: v24.1.0                       │  ← 输出（同一个黑块 ✗ 不高亮）
└─────────────────────────────────────┘
```

- 纯黑底：`pi-bridge.style.bashBg`（清空跟随主题）
- 命令行用 shiki（`shellscript`）✗ **输出不走高亮**（大文本 ✗ 且流式时是累积全文 ✗ 每包重渲染）
- 状态仍靠 `isError`（数据里**没有** exitCode ✗ 实测确认）

### 实测过的数据契约（容易搞错 ✗ 记下来）

```
① bash 参数只有一个 command          ⇒ 参数区不走通用键值对
② 结果里【没有 ANSI 颜色码】         ⇒ 不需要写 ANSI 还原（pi 的 tool-result-processor 剥掉了）
③ tool_execution_update 是【累积全文】⇒ 前端整块替换（不是追加）
   单次调用内严格前缀关系（66 包实测 ✗ 唯一断点是换了一次调用）
④ 结果里【没有 cwd / exitCode】       ⇒ 提示符只能用前端记的"当前 cwd"（旧气泡会失真 ✗ 用户认可）
```

## 四、read / write / edit 渲染器

| 工具 | 数据 | 渲染 |
|---|---|---|
| `read` | 参数 `{path}` ✗ 结果 = 文件内容 | 路径 → 摘要行；内容按扩展名：`.md` → **复用正文 Markdown 渲染器** ✗ 代码 → shiki + 行号 ✗ 其他 → 等宽 |
| `write` | 参数 `{path, content}` ✗ 结果只有一句 "Successfully wrote…" | 路径 → 摘要行；内容取**参数**的 `content`（结果里没有 ✗） |
| `edit` | 参数 `{path, edits[]}` ✗ 结果 `details.patch` | 路径 → 摘要行；`details.patch` 渲染成 diff（增绿删红 + 行号）|

### ★ edit 的 diff 是 pi 给的（不用自己算）

```
details.diff        紧凑版（" 1 …\n+5 …" ✗ 只有新行号 ✗ 没有删除行）
details.patch       标准 unified diff（★ 用这个 ✗ 有增有删）
details.firstChangedLine   第一处改动的行号
```

渲染时**文件头 `---`/`+++` 丢掉**（路径已在摘要行）✗ hunk 头弱化 ✗ 行号从 `@@ -a,b +c,d @@` 自己算（unified diff 不带逐行行号）。

### 行号的实现

```
★ 不给 shiki 的输出拆行（会切碎 token）
  而是用它自带的 <span class="line"> + CSS 计数器：
     .code-block.with-ln { counter-reset: ln var(--ln-start, 0) }
     .line::before { counter-increment: ln; content: counter(ln) }
★ --ln-start 让"尾部片段"接真实行号（第 21 行就显示 21 ✗ 不从 1 重编）
```

### 折叠：两版 DOM（只切显示 ✗ 不重渲染）

```
展开版 = shiki 渲染【全文】
收起版 = shiki 渲染【头 N 行】+ "已折叠 N 行" + 【尾 M 行】
★ 每次喂给 shiki 的都是完整行 ⇒ token 不碎 ✓ 高亮正确 ✓
★ 两版都预先建好 ✗ 切换只切 CSS 显示 ⇒ 不闪 ✓
```

用户："复用正文渲染器这种东西，难道不应该做成公共基础设施吗？语义上还是区分一下"

## 五、命令摘要（数据管线 ✗ 宿主侧解析）

```
pi 事件 tool_execution_start
  → 宿主 extractCommands(cmd)          src/panels/cmd-summary.ts（bash-parser 出 AST）
      遍历 AST 收 Command 节点 ✗ 跳过前缀词（sudo/xargs…）✗ 展开后缀找真命令 ✗ `[`→test
  → chatView.post("cmdSummary", { callId, commands })
  → 前端 showCmdChips() → 摘要行（等级色 + emoji）
```

### ★ 为什么放宿主侧

```
bash-parser + babylon ≈ 632KB ✗ 放前端会进 chat.js ✗
放宿主 = 不增加前端包 ✓ 解析失败也不影响渲染 ✓ 前端只收一个字符串数组 ✓
★ 也确认了 VS Code 【没有】命令解析的公开 API
  （它的 bash 扩展也是外挂 bash-language-server 才能解析 ✗ 说明这不是内建能力）
```

### 历史会话怎么办（★ 用户提的三个方案）

```
问题：摘要是我们实时算的 ✗ 会话文件里没有 ⇒ 重放时没有摘要行

用户提的方案：
  ① 中间缓存   ② 结果缓存（命令→命令数组）   ③ 写进会话文件/状态文件

结论：
  ❌ ③ 绝对不能写会话文件（那是 pi 的资产 ✗ 且 pi 自己也在写 ✗ 并发有损坏风险）
  ⚠️ ①② 可行但不划算（bash-parser 一条 1~5ms ✗ 50 个工具块也就 100~250ms ✗
       而重放整个会话本来就要几百毫秒 ⇒ 这点开销不算钱 ✗ 加缓存反而引入失效/体积/清空策略的负债）
  ✅ 采用：★ 不缓存 ✗ 重放时重算（repushCmdSummaries 遍历历史消息里的 bash toolCall ✓）
```

## 六、★★★ 暴露出来的架构缺陷（本轮最值钱的发现）

### 现象（用户自己诊断出来的）

> "是不是框架不合理、不优雅？每个地方自己做了一套，整体很割裂，
>  每个地方都要单独做一套，没有统一？"

### 证据（就在代码里）

```
【路径 A】实时 patch 流      apply.ts 的 case "toolStart"/"toolEnd"/"toolResult"/"toolExecEnd"
【路径 B】snapshot 全量重放   replaySnapshot() 里【又写了一遍】：
        createToolBubble → renderArgs → renderResultParts → setToolState
★ 同一个工具气泡有【两条创建路径】✗ 填充逻辑两份 ⇒ 漏一处是【结构性必然】

已经造成的：
  · cmdCache（命令摘要）只加在 A ⇒ 改配置触发重画后【摘要消失】（用户报的）
  · details（edit 的 diff）只加在 A ⇒ 切会话后【diff 会消失】（还没暴露 ✗ 必然发生）
  · dataset.streaming 前人【手动在 B 里补了一次】⇒ 说明这个坑早有人踩过
```

### 应该长什么样

```
★ 一个气泡的数据 → 一个填充函数

  fillToolBubble(bubble, data)      ← 数据的【唯一渲染入口】
      data = { args, parts, details, commands, isError, executing }

  路径 A（实时）：patch 到达 → 更新 data → 调 fillToolBubble
  路径 B（快照）：snapshot 带完整 data → 直接调 fillToolBubble
  ★ 两条路走同一份代码 ⇒ 不可能再漏
```

再往前一步 = **数据与渲染分离**：前端维护 `Map<callId, ToolData>` ✗ 所有 patch 只改数据 ✗
然后重画受影响的那个气泡 ✓ 这才是"气泡状态机"该有的样子 ——
现在状态散在 **DOM 属性（`dataset.xxx`）+ 几条渲染路径** 里 ✗ 没有一份权威的"气泡数据"✓

### 改良计划（用户认可 ✗ 本轮末尾开工）

| 步骤 | 内容 | 风险 |
|---|---|---|
| **1** | 抽 `fillToolBubble(bubble, data)` ✗ 路径 A/B 都调它 | 低（搬运 ✗ 行为不变） |
| **2** | 前端加 `toolData: Map<callId, data>` ✗ `cmdSummary`/`details` 到达时**重填**而不是"当时填一次" | 低 |
| **3** | （以后）流式更新也归约成"改数据 + 局部重画" | 中 |
