## 二、图标 401：主路径 + data URI 自动降级

### ③ 诊断设计（★ 一次实验给根因 ✓）

用户否了"直接换 data URI"✗ 要求**先诊断** ✓ 于是设计成**同一页面双路径对照**：

```
img1 = asWebviewUri 生成的地址   ← 现状（预期 401 ✓）
img2 = 同一张图的 data URI       ← 新（预期成功 ✓）

结果矩阵：
  img1 成功              → 问题是别的（缓存/时序）→ 继续查 ✓
  img1 失败 & img2 成功  → ★★ 渲染路径没问题 ✗ 是 URL 授权链坏 ✓
  两个都失败             → 渲染路径本身有问题（CSP / service worker）✓
```

**实测结论**（用户贴的日志 ✓）：
```
[warning] 图标主路径失败 → 改用 data 兜底：test-args
  src = https://file+.vscode-resource.vscode-cdn.net/... 
★ 而且图标【显示出来了】✗ ⇒ 第二行命中 ✓
```

### ④ ★★ CSP 的一个坑：`img-src *` **不包含** `data:`

```
chat.html 原本是：img-src *;
★ 但 CSP 规范里 `data:` 是【单独一个 scheme 源】✗ 通配 * 不含它 ✓
⇒ 必须显式写：img-src * data:;
★ 差点漏掉 ✗ 漏了的话 data URI 会被 CSP 拦 ✓（症状完全不同 ✗ 更难查 ✓）
```

### ⑤ 实现：两条路都给，失败自动降级

```ts
// main.ts
iconForWeb(icon) → { icon: <webview URI>, iconData: <data URI> }
  · 上限 128KB（超了只给主路径 ✓ 防用户塞大图 ✓）
  · 读不出文件 → 只警告 ✗ 不崩 ✓

// cmdrail.ts
1. 主路径可用 → 先用它（★ 保留诊断能力 ✓）
2. error → 记进 useFallback 集合 ✗ 改用 iconData ✓
3. 以后重绘时直接走 data ✗ 不再白闪 ✓
```

★ **为什么不直接用 data URI？**（用户问过 ✓）
```
· 主路径是【标准做法】✗ 万一环境修好 ✗ 自动回到正轨 ✓
· 保留一次失败尝试 = 保留证据（日志里能看到 401 还在不在 ✓）
· 代价只有第一次的"白闪一下"✗ 用户说保持现状 ✓
```

### ⑥ 性能核算（★ 用户问的 ✗ 我算了才敢答 ✓）

| 环节 | 成本 |
|---|---|
| 宿主 `readFileSync` + base64 | ★ **照旧存在** ✗ 只多一次编码：10KB → ~0.1ms |
| postMessage 体积 | base64 比原图大 **33%** ✗ 20 个图标 → 267KB ✗ 几毫秒 |
| webview 解码 | 内存操作 ✗ 无网络 ✓ |
| **调用频率** | ★ 关键 ✗ `pushCommands()` 只在 **onReady + 配置变化**跑 ✗ 不是流式 ✓ |

⇒ 结论：**没有实际性能问题** ✓ 但边界要记住（>100 个图标 / 单个很大时要再想 ✓）

### ⑦ ★ 一个概念纠正（用户的理解 ✗ 我说清了 ✓）

用户问："你的兜底方案就是把整个图片直接作为数据传进去，而不是 I/O？"

```
★ I/O 没有消失 ✗ 它换了位置：

主路径（坏掉的）
  webview ──HTTP──> VS Code 资源代理 ──读磁盘──> 返回     ← 多一层代理（那层坏了）

兜底（现在的）
  宿主 ──fs.readFileSync──> Buffer      ← ★ 这一步就是 I/O ✗ 没消失
  宿主 ──base64──> 字符串               ← 内存操作
  宿主 ──postMessage──> webview         ← 进程间消息
  webview ──<img src="data:...">        ← ★ 无网络请求 ✓

⇒ 一句话：把「运行时拉取」换成了「推送时内联」✓
   收益：不依赖环境那条链 ✓
   代价：消息体积 +33% ✗ 和丢掉「按需加载」✓
```

## 三、参数收集「独立窗口」

### ⑧ ★ 复用交互面板（用户的想法 ✓ 洞察很准）

```
用户原话：
  “复用交互面板 ✗ 它已经有 select / confirm / input / editor 四种控件
   参数收集只需要 select + input ⇒ 完全覆盖
   唯一要处理的是【来源】：pi 的请求 → 回复给 pi；我们自己的 → 拼命令注入
   ⇒ 给面板加一个 source 字段就够了”✓

★ 为什么这个复用成立？→ 形状完全一样：
   交互面板的「答卷模式」= 一次填多题 + 一次性提交 ✓
   参数收集            = 一次填多参数 + 一次性拼装 ✓
```

### ⑨ 关键实现

```
① UiReq 加两个字段
     source?: "pi" | "local"     ← 只影响文案 ✓
     taskId?: string             ← 本地任务分组 ✓

② 宿主维护两张表
     localTasks: Map<taskId, { item, values, need, reqIds, idToField }>
     reqToTask:  Map<reqId, taskId>        ← 答复回来时反查 ✓

③ ★★ 请求 id 必须加 task 前缀
     id = `${taskId}:${field.id}`
   【为什么？】field.id 在配置里是稳定的 ✗
     同一按钮点两次 → 两个请求同 id → ★ 前端 answers Map 会串（一份答案填两题）
   ⇒ 加前缀 ✗ 再用 idToField 映射回干净的 field.id ✓

④ 分流点：handleUiResponse 的【最前面】
     const taskId = reqToTask.get(id);
     if (taskId) { handleLocalAnswer(taskId, id, r); return; }   // 本地
     ...原逻辑...                                                 // pi
     ★ 因为在最前面 ✗ 所以不会误发给 pi ✓

⑤ 面板加了两个方法
     pushMany(reqs)     ← 一次入队 + 一次 sync（不要 for 循环 push ✗ 会 N 次抢焦点）
     dropTask(taskId)   ← 取消时把该任务剩余的请求一起撤掉 ✓
```

### ⑩ 配置页的接线

```
· inputMode === "panel" → collectViaPanel(item)     ★ 终于真的走面板了 ✓
· 全 fixed 的参数       → 不用问 ✗ 直接拼装发送 ✓
· 取消（任何一题）      → ★ 整条命令不发 ✗ 并把该任务剩余请求撤掉 ✓
```

## 四、收纳器（横向弹层）

### ⑪ 弹层必须挂在 `document.body`

```
#cmd-rail 有 overflow: hidden ✗（B32 为了隐滚动条 ✓）
⇒ 弹层挂它里面会被【裁掉】
⇒ 挂 body + position: fixed ✓
★ 代价：不随内容滚动 ✓ ⇒ 必须监听 scroll / resize 关掉它 ✓
```

### ⑫ ★★ 最大的一个 bug：`makeBtn` 只造元素，忘了挂事件

```
现象（用户报的 ✗）：
  “按钮的注入是完全没有效果 ✗ 一点效果没有。我看了一眼日志也没有任何报错”✓

根因：
  openPopover 里 → el.appendChild(makeBtn(child, group))
                  ★ 只 append ✗ 没 wireClick / wireMenu
  ⇒ 按钮渲染出来了 ✗ 但【没有任何监听】✓ ⇒ 点了什么都不发生 ✓ 而且不报错 ✓

★ 修法【不是补一行】✗ 而是把事件挂进 makeBtn ✓
  ⇒ 调用方【没机会漏】✓（FACTS #26 的思路：改结构，别写注释 ✓）
```

### ⑬ 弹层的三个关闭时机

```
① 点外面（点弹层里 / 点收纳器按钮本身 → 不关 ✓ 后者自己 toggle ✓）
② Esc
③ ★ 滚动 / 缩放 —— 因为 position: fixed 不随滚动走 ✗ 不关就漂在原地错位 ✓
```
