### ③ steer vs followUp 的真实区别（源码注释原文 ✓）

```ts
// steer()    : "Delivered after the current assistant turn finishes executing
//               its tool calls, before the next LLM call."
// followUp() : "Delivered only when agent has no more tool calls or steering messages."
```

翻译 ✓：
```
steer    → 当轮工具跑完 → 【下次 LLM 调用之前】注入 ✓
           ★ AI【中途就看到】✗ 会改变方向 ✓（真正的"边跑边纠正"✓）
followUp → AI【完全停下】才注入 ✓ → 是【全新一轮】✓
           ★ 和"等它停了自己再发"几乎一样 ✓ 只是"先预约"✓
```

### ④ 架构决定：状态由【后端】维护 ✓

```
★ 为什么不在前端判断忙/闲？
   前端那份状态【有网络延迟】✗ → 会踩竞态 ✓
   （AI 刚结束 → 前端还以为在跑 → 发 steer → 消息卡在队列 ✓）

★ 后端为什么零延迟？
   pi 的事件【直接流过 main.ts 的订阅】✓
   → agent_start 置忙 / agent_settled 置闲 ✓ 立刻生效 ✓

★ 为什么不复用前端那个 agentState？
   用途不同 ✓：
     前端那份 = 视觉（转圈 / 中断按钮形态 ✓）
     后端这份 = 决策（steer 还是 prompt ✓）
   两份同源（都从事件流来 ✓）但各自独立 ✓
```

**★ 一个容易错的细节** ✗：
```
★ 只用 agent_settled 置空闲 ✗【不能用 agent_end】✗

agent_end     = "这轮产出完毕"✗ 后面【还有尾巴】✗（重试 / 队列投递 / 续写 ✓）
agent_settled = "彻底空闲（重试、队列都空了）"✓ ← 只有它能置 idle ✓

若用 agent_end：会在尾巴没跑完时误判空闲 →
   此时用户发消息 → 退化成 prompt → ★ 又被静默丢弃 ✗
```

### ⑨ 补修：动作区被输入区盖住（同日 ✓ 用户实测报的 ✓）

**现象** ✗：
```
滚到最底时，最后一条气泡的【动作区】（复制/克隆/分叉 ✓）被输入区盖住 ✗
★ 用户观察得很准：“被遮挡的不是内容，内容高度是正确的，
                    被遮挡的是下面的命令（按钮）✓”
```

**根因** ✗：
```typescript
// 旧：
messagesEl.style.paddingBottom = inputAreaEl.offsetHeight + 8 + "px";
                                       ↑ 只算了输入区 ✗
// 而最后一条气泡下面还有 ~20px 高的动作区 ✓ → 正好落在输入区后面 ✓
```

**修** ✓：
```typescript
// paddingBottom = 输入区高度 + ★ 最后一条气泡的动作区高度 + 8px 缝
export function syncPadding(): void {
    const last = messagesEl.lastElementChild as HTMLElement | null;
    const actions = last?.querySelector<HTMLElement>(".bubble-actions");
    const actionsH = actions?.offsetHeight ?? 0;
    messagesEl.style.paddingBottom = inputAreaEl.offsetHeight + actionsH + 8 + "px";
}
```

**为什么用【实测高度】而不是写常量？** ✓
```
· 空动作区是 display:none ✓ → offsetHeight = 0 ✓ 自动不预留 ✓
· 用户改了字号 / 内边距 → 高度跟着变 ✓ 写死的常量会不准 ✗
```

**★ 附带一个性能细节** ✗：
```
refreshForkButtons() 改成【返回 boolean】✓（是否真的新增了按钮 ✓）

为什么？
  · 它每次 patch 后都会被调 ✓ 而流式时 patch 是【每帧级别】的 ✗
  · 而 syncPadding() 要读 offsetHeight → ★【强制同步布局】✗（贵 ✓）
  · 若无条件重算 → 流式时每帧强制回流 ✓ → 白白卡顿 ✓
  → 只有真新增了才重算 ✓
```

### ⑩ 顺带厘清的三件事

**① `queue_update` 为什么会来两个包？**（用户问的 ✓）
```
第 1 个：steering=["我的话"]   ← 入队（_queueSteer 里 push 后立刻 emit ✓）
第 2 个：steering=[]           ← ★ 投递完成（数组已清空 ✓）

★ 第二个空数组【不是“用户手快发了空消息”】✗（空检验是有的 ✓ input.ts 的 send() ✓）
  它是 pi 的【出队信号】✓ —— 而这正好是“删掉插入条”的唯一依据 ✓
```

**② 主动中断会让插话失效** ✓ —— 符合直觉，可接受 ✓
```
abort 时 pi 会【清空队列】✓ → 插话自然没了 ✓
★ 而且我们会收到 queue_update（steering 变空 ✓）→ 插入条自动消失 ✓
  （不会留下“假排队”的残影 —— 这点很重要 ✗）
```
