# B40（详细记录）

> 本轮做的是 B39 第五节欠下的账：**让"漏字段"变成编译期错误**。
> 起因很丢人 —— B39 里我自己漏传了一个字段（`details`），而 `Partial<T>` 让这个漏
> **合法地溜过了编译** ✗ 直到用户实测说"还是老样子"才暴露 ✓
> ★ 结论：靠人肉对齐字段是不可靠的 ✗ 要让**编译器**去对齐 ✓

---

## 一、问题定性（为什么这不是"下次小心"能解决的）

```
B39 的 bug 长什么样：
  · replaySnapshot 漏传 details          —— 单独看这处代码，完全正常
  · SnapBlock 类型里没有 details         —— 单独看，也正常
  · 只有【把两处放在一起对比】才看得出问题 ⇒ 而 grep 做不到这件事
★ 而且 TS 还帮忙掩护：fillToolBubble(bubble, patch: Partial<ToolData>)
   ⇒ Partial ⇒ 少传字段是【合法】的 ⇒ 编译通过 ⇒ 运行时才发现
```

**所以目标不是"记得写全"，而是**：让"写不全"这件事**没法通过编译**。

---

## 二、四个动作

### ① 前端守门：快照路径用【必填】形状

```ts
// src/webview/tool.ts
export interface ToolSnapshotData {
    args: unknown;                          // ★ 不用 `?` ✗ 值可以是 undefined
    resultParts: unknown[] | undefined;     //    但【键必须写出来】
    partialParts: unknown[] | undefined;
    resultIsError: boolean | undefined;
    executing: boolean | undefined;
    details: unknown;
    commands: string[] | undefined;
}
export function fillToolBubbleSnapshot(bubble, data: ToolSnapshotData)   // ★ 快照专用入口
```

调用它就必须**列出所有字段** ✗ 少一个 ⇒ `error TS2741: Property 'details' is missing`

**★ 附带一个键一致性断言**（防止加字段时只改一半）：

```ts
type KeyMismatch<A, B> = ...;   // 两边键集合不一致时 <不是 never>
const _keysInSync: KeyMismatch<ToolData, ToolSnapshotData> extends never ? true : false = true;
// ⇒ ToolData 加了字段却忘了同步 ToolSnapshotData ⇒ 编译错误
```

⚠️ 踩的坑：本来想用映射类型 `{[K in keyof ToolData]-?: ToolData[K] | undefined}`
✗ 实测**不保留 undefined**（`-?` 会把 undefined 一起去掉 ⇒ 传 undefined 反而报错）✓
⇒ 改成手写接口 ✓ 反而更清晰 ✓

### ② 宿主收口：`tool-facts.ts`（★ 读 pi 数据只有一处）

```
数据进宿主有【多条通道】✗ 每条形状都不一样：

  通道                      形状
  ──────────────────────────────────────────────────────────
  message_start            { message: { role, content, details, isError, toolCallId } }
  会话文件回放              { role, content, details, isError, toolCallId }   ← 少一层
  tool_execution_end       { toolCallId, isError, result: { details } }        ← details 埋一层

各自去 .details 的后果 = 某条通道漏读某个字段（B39 就是这么来的）
⇒ 收敛到 readToolResultMessage() / readToolExecutionEnd()
  ★ 字段名只写一遍 ✗ 通道只负责"把原料递进来"
```

### ③ 类型统一：`ToolBlockFields`（★ 本轮最实在的一步）

```
原先工具字段在【四个地方】各手写一遍：
  Block（宿主气泡）· SnapBlock（前端快照）· ToolData（前端渲染入口）· ToolSnapshotData
★ 而且命名还不一致：宿主叫 resultIsError ✗ 前端自己翻译成 isError ✗✗
  ⇒ "同义异名"就是漏字段的温床（翻译层永远会漏一处）

现在：
  src/view/chat-types.ts
      export interface ToolBlockFields { toolName? toolCallId? toolDone? argsText? args?
                                         resultParts? resultIsError? details? partialParts? executing? }
              ↑ 唯一来源
      Block     extends ToolBlockFields        （宿主气泡）
      SnapBlock extends ToolBlockFields        （前端快照）
      ToolData  = Pick<ToolBlockFields, ...>   （前端渲染入口 ✗ 只取用得上的）
  ★ 加字段 / 改名 ⇒ 只改一处 ⇒ 对不上就编译错误
```

### ④ 命名统一：`isError` → `resultIsError`

前端内部跟着宿主用 `resultIsError` ✗ **取消"翻译层"** ✓
（`ChatPatch` 协议层的 `isError` 保持不变 —— 那是另一层 ✓）


## 四、数据表示的层次（为什么不能一把合并）

排完之后还剩 4 处 `details?: unknown` ✗ 看起来"没统一干净"✗ 但它们是**不同层**：

```
① pi 原始数据       message / event 对象           （format-backend 里读）
② 协议层 ChatPatch  宿主 → 前端 的 patch            （toolResult / toolExecEnd / …）
③ 气泡数据          ToolBlockFields                （宿主 Block / 前端渲染入口）
④ 会话文件消息      ReplayMessage                  （replay.ts 读 jsonl）
★ 每层职责不同 ⇒ 无法合并 ✗ 但【每层内部只有一处定义】✓ 这就是能做到的极限 ✓
```
