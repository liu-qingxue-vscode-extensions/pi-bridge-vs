## 一、代码块缩放（①）

### 三类内容的形态不同 ⇒ 处理方式必须不同

```
bash 输出    .part-text   white-space: pre-wrap   → 折行
diff 行      .diff-lc     white-space: pre-wrap   → 折行
read/write   .code-block  white-space: pre       → ★ 不能折行
```

**为什么代码不能折行**：折行会把 `if (a && b) {` 拆成两行 ⇒ 看起来像两条语句 ✗
缩进层级和括号配对全乱 ✓（代码的"结构"被破坏）

⇒ 代码类的溢出用**缩放**，不用折行 ✓

### 实现

```
src/webview/code-fit.ts
    fitCodeBlocks(root)
        ① 先复位 --code-scale（★ 不复位的话，上次的缩放会污染这次的测量 ⇒ 越缩越小）
        ② 量：pre.scrollWidth（内容真实宽度）vs pre.clientWidth（可用宽度）
        ③ 缩：scale = avail / need ✗ 下限 0.75（缩到看不清还不如让用户横向滚）
    触发：每次渲染后（refold 里）+ 面板/窗口宽度变化（ResizeObserver ✗ 节流到下一帧）
CSS： .code-block pre { font-size: calc(100% * var(--code-scale, 1)) }
配置：pi-bridge.style.codeAutoFit（默认开 ✗ 关掉回到横向滚动）

★ 范围天然精确：.code-block 只有 read/write 和 markdown 代码块在用
  （bash 用 .part-text ✗ diff 用 .diff-lc）⇒ 不会误伤 ✓
```

## 二、跳转编辑器（② ★ 本轮主角）

### 核心问题：编辑器只能显示【文本】

webview 里的东西是 DOM（HTML/组件 ✗ 编辑器吃不了）✗
所以"扔过去"本质上是**丢文本**，区别在于**让 VS Code 怎么呈现**。

### 虚拟文档（不落盘）

```
✗ 写 /tmp/xxx.txt 再打开  → 文件堆积 / 要清理 / 多窗口冲突 / 用户在 /tmp 看见垃圾
✓ TextDocumentContentProvider（VS Code 正统做法）
    注册 scheme = pi-view:/
    编辑器要显示时问我们"这个 URI 内容是什么" ✗ 我们现答 ✓
    好处：不落盘、零清理、可以 diff、URI 路径带扩展名就能触发语法高亮 ✓
```

### 按内容类型分派

| 工具 | 呈现 | 做法 |
|---|---|---|
| read / write | **真实文件** | 有 path ⇒ `showTextDocument`（可编辑 ✗ 有语言服务 ✓）|
| **edit** | ★ **真 diff 视图** | `vscode.diff(改前, 改后)` |
| bash / 扩展工具 | 虚拟文档 | 只读文本（扩展工具走 default 分支 ⇒ 将来加一个 case 就能特化）|

### ★ 点睛之笔：diff 视图的右边用【真实文件 URI】

```
vscode.diff(左边, 右边, 标题)
  左边 = 虚拟文档（反推出来的"改前"）
  右边 = vscode.Uri.file(路径)   ← ★★★ 不是虚拟文档 ✗ 就是那个磁盘上的活文件 ✓
⇒ 于是 VS Code 打开的是【真正的 diff 视图】✗ 右边还能就地编辑保存 ✓✓
  跟"在 Git 里点开一个改动"完全一样的体验 ✓
```

### ★ patch 反推（本轮唯一的算法）

```
问题：diff 视图需要"改前"的内容 ✗ 但磁盘上只有"改后"
答案：details.patch 里同时含改前改后的信息 ⇒ 相减即可 ✓ 不必依赖 git / 历史 / 备份

依据（unified diff 语义）：
   " " 上下文行 → 两边都有，内容相同
   "-" 删除行   → 只在 before 有
   "+" 新增行   → 只在 after 有
   @@ -a,b +c,d @@ → 这一段在 after 里从第 c 行开始（1-based）
                      ⇒ hunk 之间的行两边完全一样 ⇒ 直接拷贝 ✓

★ 刻意放在 src/bridge/patch-reverse.ts（零 vscode 依赖）
  ⇒ scripts/check-patch-reverse.mjs 能直接喂字符串测它 ✓
```

### 守门：scripts/check-patch-reverse.mjs（7 个用例 ✗ 已接进 compile）

```
① 真实数据（用户测试文件的"一行改一行"）
② 纯新增  ③ 纯删除
④ 多 hunk（★ hunk 之间的内容不能被吃掉）
⑤ 末尾无换行（\ No newline 标记要跳过）
⑥ 空 patch（原样返回）  ⑦ 多行替换（3 行 → 2 行）
```

**它当场抓过一次问题** ✗ 虽然最后判定是**测试数据自己不自洽**
（我在 after 里放了一行 patch 说"已被替换掉"的内容 ✗ 算法正确地吃掉了它 ✓）
★ 但它逼我重新把算法手算了一遍 ⇒ 结论是算法对 ✓ 单测的价值在这 ✓

## 三、★★ 本轮踩的两个坑（比功能本身值钱）

### 坑 1：漏 import `vscode` ⇒ 运行时静默失败

```ts
const open = () => { vscode.postMessage({...}); };   // ✗ 文件里没 import vscode
```

**症状**：按钮点了完全没反应（不报错 ✗ 不提示 ✗ 就是没动静）
**为什么**：`vscode` 是运行时才注入的全局 ✗ 漏 import 的话它是 undefined ⇒
调用时抛 `ReferenceError` ⇒ 而事件处理器里抛错不会弹任何东西 ✓

**★ 但 tsc 其实【会】拦它**（TS2304: Cannot find name 'vscode'）✗ 为什么没拦到？

```
compile 的顺序是：
  tsc -p ./                              ← ★ 在这一步先报【别的错】(TS2459) ⇒ 立即停下
  node scripts/check-patch-reverse.mjs   ← 没跑到
  tsc -p tsconfig.webview.json --noEmit  ← ★ 本该在这里报 vscode 未定义 ✗ 也没跑到
★ 而我当时 grep 的输出用了 `head -6` ⇒ 只看见第一个错
```

**⇒ 教训不是"tsc 不行"，而是"看输出的方式"把它掩盖了** ✓
（后来我特意用一个假变量名验证过：`tsc -p tsconfig.webview.json` 确实会报 TS2304 ✓）

### 坑 2：用脚本切文本删代码 ⇒ 把 import 块一起切掉

```
删一个不再用的常量时，用 python 的 s.index(...) 取区间 ⇒ 区间取大了
⇒ 报 Cannot find name 'ui' / 'createHead' / 'makeActions'（一堆）
⇒ 修法：用 git show HEAD:文件 取【原始 import 列表】重建 ✓ 最可靠
★ 这跟之前"正则贪婪删错代码"是同一类 ⇒ 以后删代码先打印待删片段确认 ✓
  或者干脆用 edit 工具（精确匹配 ✗ 不会误伤 ✓）
```
