## 二、做了什么

### ① 唯一填充入口 `fillToolBubble`

```ts
// src/webview/tool.ts
interface ToolData { args?, resultParts?, partialParts?, isError?, executing?, details?, commands? }
const toolDataMap = new WeakMap<HTMLElement, ToolData>();   // 气泡 → 数据（权威状态）

fillToolBubble(bubble, patch: Partial<ToolData>)
    ├ ① commands → showCmdChips      （摘要行）
    ├ ② args     → renderArgs        （参数 / 命令行 / 路径行）
    ├ ③ parts    → renderResultParts （最终结果 ?? 流式内容）
    ├ ④ details  → renderDiffDetails （必须在 ③ 之后：它要挡住 ③ 的覆盖）
    └ ⑤ 状态     → setToolState
```

**两个设计点**：

```
a) undefined 的字段【被忽略】✗ 不清掉已有的值
   （snapshot 里 resultParts 为 undefined ≠ 要抹掉流式内容）
b) 内部各渲染函数【都是幂等的】（先清空再填）⇒ 可以随便重复调
   ★ 这是能合并的前提（先验证过才动手 ✓）
```

### ② 六条 patch 分支 + snapshot + cmdSummary 全部归约

```
apply.ts 里已无任何"散装"调用 ✓（grep 验证：renderArgs( / renderResultParts( … 均为 0）
净减 41 行
```

### ③ 顺带修复：重放后 edit 的 diff 消失（★ 本轮真正的用户可见收益）

顺着"数据从哪来"追下去，发现 **`details` 在三个地方断了**：

| 环节 | 问题 |
|---|---|
| `replay.ts` | `toolResult` patch 没带 `details`；`ReplayMessage` 也没声明这个字段 |
| `chat-types.ts` | `Blk` 和 `toolResult` patch 的类型里没有 `details` |
| `chat-state.ts` | `toolResult` / `toolExecEnd` 时没存 `blk.details` |
| `format-backend.ts` | `message_start`（pi 推消息那条路）没取 `details` |
| `apply.ts` | ★ snapshot 重放时忘了往下传（**我自己漏的**，见第五节）|

## 三、★ 数据通道的澄清（实测数据包得出结论）

这一节是**给以后省时间**的：

```
┌ 通道 A：请求-响应 ────────────────────────────┐
│  我们主动发 {type:"get_messages"}              │
│  pi 用 {type:"response", command:"get_messages"} 回  │
│  ★ 字段完整（含 details.patch ✓ 实测确认）      │
└───────────────────────────────────────────────┘
┌ 通道 B：pi 主动推的事件 ──────────────────────┐
│  message_start / message_update / tool_execution_* │
│  ★ 切换会话时 pi【推】历史（走这条）           │
└───────────────────────────────────────────────┘
```

### ★ 关键实测：切换会话到底走哪条

用户导出的数据包（`test_date/pi-debug-20261007-061507.json`，15 包）：

```
[12] response  command=switch_session        ← 点了切换
[13] response  command=get_messages  messages=9  ← ★ 拉了历史
[14] response  command=get_state
```

⇒ **切换会话 = 我们主动拉**（通道 A）✗ 不是 pi 推 ✓

**为什么值得记**：我一开始以为是 `message_start`（通道 B）✗ 因为
"我加在 `replaySessionMessages` 里的日志没打印 ⇒ 那条路没跑"这个推断**方向反了**
——日志没打印的真实原因是**用户还没 F5（跑的是旧代码）** ✓
★ 教训：**"日志没打印"要先排除"代码没生效"** ✗ 不要直接推论"那条路没走" ✓

### ★ 顺带确认：会话文件里 details 一直在

```
toolResult 消息顶层就有：role / toolCallId / toolName / content / details / isError / timestamp
edit 的 details = { diff, firstChangedLine, patch, processedBy }
★ `details.patch` 就是统一 diff（有增有删 ✓ 我们用这个）
★ `details.diff` 是紧凑版（只有新行号 ✗ 没有删除行）
```

## 五、★★ 我自己踩的同一个坑（下一轮的动机）

修完之后用户说"**还是老样子**"✗ 因为我：

```ts
// apply.ts 的 replaySnapshot 里
fillToolBubble(last, {
    args: blk.args,
    resultParts: blk.resultParts,
    partialParts: blk.partialParts,
```
