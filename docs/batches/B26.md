## 二、★★ 串行 vs 并行的真相（本轮最重要 ✗）

### ④ 最初的现象

```
用户测 ask-user-question 扩展：4 个问题【一个一个】弹出来 ✗
用户观察调试板：“我点一下它才弹出第二个数据包”✓
```

### ⑤ 我犯的错误 ✗（记下来防复犯）

```
★ 我看数据包发现 4 个 extension_ui_request 的 index【连续】✗
   → 就断言“背靠背发出 = 并行”✗✗✗ 【错】
★ 用户反驳得对 ✓：
   串行时你在答题 ✗ pi 在等 ✗ 【期间没有任何事件】✗
   → 下一个 request 的 index 也是 +1 连续 ✓
   ⇒ ★【index 连续根本无法区分串行和并行】✗
```

★ **教训** ✗：数据包里没有时间戳 ✗（只有 payload ✓）→ 不能从 index 推时序 ✓

### ⑥ 找到根因（源码铁证 ✓）

pi 源码 `dist/modes/rpc/rpc-mode.js`：

```js
async custom() {
    // ★ Custom UI not supported in RPC mode
    return undefined;
},
setEditorComponent() { /* Custom editor components not supported in RPC mode */ },
```

pi 官方文档 `docs/rpc.md:1195` 也写死了 ✓：

```
Some ExtensionUIContext methods are not supported or degraded in RPC mode
because they require direct TUI access:
- custom() returns undefined
```

### ⑦ 那个扩展自己做的分流（`rpc-fallback.ts` 的注释 ✓）

```ts
// RPC hosts (VSCode pendant, ACP clients like Zed/Paseo — issue #78):
// ui.custom() cannot render there, but the select/input dialog
// sub-protocol works. Hosts that advertise ctx.mode (pi ≥0.79) route to
// the sequential dialog walker up front...
if ((ctx as {mode?:string}).mode === "rpc" && hasDialogUI(ctx.ui)) {
    return runRpcPath(pi, ctx.ui, typed);   // ★ 串行的 dialog walker ✗
}
const result = await ctx.ui.custom<QuestionnaireResult>(...);   // TUI 路径 ✓
```

其 `rpc-fallback.ts` 第 92 行的实现 ✓：

```js
for (let qi = 0; qi < params.questions.length; qi++) {
    const answer = q.multiSelect
        ? await askMultiSelect(ui, q, qi, header)    // ★ await 一个个来 ✗
        : await askSingleSelect(ui, q, qi, header);
}
```

★ **注意** ✗：`mode` 是 **pi 主动告诉扩展的**✗ 不是我们能控制的 ✓
★ **多选退化成 `ui.input`**✗ 所以数据包里出现 `placeholder = "1,3"` ✓✓（手填编号 ✓）

### ⑧ ★★ 结论（三方责任划分）

| 谁 | 情况 | 能否改进 |
|---|---|---|
| **pi 本体** | `custom()` 在 RPC 下返回 undefined ✗ | 架构性（函数无法跨进程 ✗）**但**可以加一个「批量 UI 描述」协议 ✗ 现在没有 ✓ |
| **扩展** | RPC 降级选了**串行**✗ | ★ **完全可以改 Promise.all 并行**✗ 几十行 ✓ 可提 PR ✓ |
| **我们的前端** | ★ 完全无辜 ✓ | pending 里有几个**由扩展决定**✗ 前端改不了 ✓ |

## 三、答卷模式 + 累积多页（实现）

### ⑨ 分层判定（用户定的 ✓）

```
★ 判定点 = 【用户提交那一刻看队列有几个】✗
   队列 == 1 → 单题模式：答完【立刻发】✓
      （可能是串行扩展的第 1 问 ✗ 不回它就永远不发第 2 问 ✓）
   队列 >= 2 → 答卷模式：可切页 + 确认页 + 一次性提交 ✓
      （★ 能到 2 个 ⇒ 必定是并发 ✗ 因为串行的第 2 个要等你回第 1 个 ✓）

★ 为什么不需要人为聚合窗口？→ 两种判定其实等价 ✓
   并发的第 2 个是【毫秒级】到 ✓ 你看的时候队列已齐 ✓
   串行的第 2 个要等【你提交】才可能出现 ✓ 永远不会提前到 ✓
```

### ⑩ ★★ 串行也做成「多页问卷」（关键 ✗）

```
串行时：answer 一个 → 立刻发 ✓ → 移入 history ✗ → 页签变绿 ✓
        扩展毫秒后发下一题 ✗ → 页签 [1][2] ✗ → ★ 自动翻到新题 ✓
        ... 最后一个 → 600ms 后关面板 ✓
★ 观感与 TUI 的多页问卷一致 ✓
★ 唯一差别：历史页【只读】✗（答案已经发出去了 ✗ 协议死限 ✓）
```

**实现要点** ✗：

```
state.history: Array<{q, a}>       已答已发的历史 ✓
state.page                          页码（允许 == totalPages()✓ = 虚拟“等待页”✓）
advanceToNextUnanswered()           ★ 只往后找未答的 ✓ 不跳确认页 ✓
applyQueue() 过滤 history           ★ 否则宿主的 sync 会把已答的推回来 ✓
```

### ⑪ ★ 修掉一个设计缺陷：「改内容」和「提交」必须解耦 ✗

```
★ 问题：如果“内容变化”就等于“提交”✗
   串行模式下用户在「✍ 自己写…」框打第一个字 → 答案就发出去了 ✗✗✗
   （然后扩展立刻发下一题 ✗ 后面打的字全丢 ✓）
★ 修法：两个回调 ✗
   onDraft  内容变了 → 【只写草稿】✗ 绝不提交 ✓
   onCommit 明确动作（选项点击 / Enter / Ctrl+Enter）→ 才提交 ✓
★ 另外：正在文本输入时不重绘 ✗（否则光标跳回末尾 ✓）
```

### ⑫ 交互细节（用户要的 ✓）

```
· ★ 答题瞬间自动跳到下一题 ✓（不跳确认页 ✓；用户手动回看历史时【不拽走】✓）
· ★ select 补上「✍ 自己写…」✗（TUI 里每个问答都有 ✓）
· Enter 提交（input ✓ editor 用 Ctrl+Enter ✗ 保留换行 ✓）
· ★ ← → 键盘翻页 ✓（在输入框里打字时不抢 ✓ 留给光标 ✓）
· ★ 显示区域居中 ✗ 内容左对齐 ✓（max-width 1000px + margin auto ✓）
· 控件加大 ✗（按钮 min-height 38px ✓ 输入框 40px ✓ textarea 220px ✓）
```

## 四、hack pi 本体的可行性调查（结论：不可行 ✗）

### ⑬ 有没有统一的发送位置？

```
★ pi 的扩展 API（dist/core/extensions/types.d.ts ✓）：
   on("ui_prompt_start", handler)  ✓ 有 ✗
   on("ui_prompt_end", handler)    ✓ 有 ✓

★ 但 UIPromptStartEvent 只有 4 个字段 ✗：
   { type, reason, kind, title }   ← ★ 没有 id ✗ 没有返回值类型 ✗
★ 对比 ToolCallEvent 有 ToolCallEventResult（能 block / 改写 ✓）✗
   ⇒ ★ UI hook 是【纯通知】✗ 只能观察 ✗ 不能改写 ✓
★ 而且 ui 请求走 output() 直接写 stdout ✗ 不经过事件系统 ✓
```

### ⑭ 三条硬结论

```
① pi 侧【没有统一的数据包发送位置】可 hook ✗
② 即使能改写也没用 ✗ ——「串行」的根因是【扩展代码里的 for + await】✗
③ ⇒ “写 hack 插件让 pi 并发发包” ★ 做不到 ✗
★ 不该做的事：hack pi 本体 ✗（违反扩展契约 ✗ pi 一升级就碎 ✓）
```
