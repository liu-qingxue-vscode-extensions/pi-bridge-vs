## 一、先把"压缩"这件事搞清楚（挖 pi 源码）

### 1.1 数据长什么样（实测会话文件）

```
type=compaction 条目：
    summary            ← 摘要文本（实测 41KB）
    firstKeptEntryId   ← ★ "从这里开始保留"的指针
    tokensBefore       ← 压缩前的 token 数（实测 633,357）
    usage / details / fromHook / systemMessage
```

### 1.2 语义（`session-manager.js` 的 `buildContextEntries`）

```js
path = 从当前 leaf 沿 parentId 回溯到 root       // ★ 是【树路径】不是文件顺序
找 path 里【最新】的 compaction（老的直接忽略）
结果 = [ 最新的 compaction ]                     // ★ 它自己变成一条摘要消息
     + [ firstKeptEntryId … 之后 ] 的条目         // ★ 保留
     + [ compaction 之后的全部 ]
⇒ firstKeptEntryId 【之前】的条目统统丢弃
```

**用户的模型（正确）**：

```
第 1 次压缩：材料 = [第1…10轮 原文]                  ⇒ 结果一
第 2 次压缩：材料 = [结果一] + [第11…20轮 原文]       ⇒ 结果二（替代前20轮）
```

**源码逐字对应**：

```js
previousSummary = projectedEntries[prevCompactionIndex].sourceEntry.summary;  // 用户的"结果一"
boundaryStart   = prevCompactionIndex + 1;                                   // 用户的"第11轮起点"
promptText += `<previous-summary>…</previous-summary>`;                      // 一起喂进摘要模型
```

**要补的精确点**：
- 文件是 **append-only** ⇒ **一个字都没删** ✗ 只是"读的时候按指针跳过" ✓
- **只有最新那个 compaction 有效** ✗ 老的在投影里贡献为空 ✓
- 两个数字之间（compaction 事件 vs 指针位置）差 41 条 ⇒ 因为**文件顺序 ≠ 树路径顺序** ✓
- **不是"每次从头压"**：铁证是两次 `tokensBefore`（633,357 → 568,377 ✗ 第 2 次反而更小 ✓）

### 1.3 落地：只显示一个压缩气泡

```ts
// bridge/session-file.ts 的 applyCompaction（照抄 pi 的语义 ✓）
· 找最后一个 compaction
· 输出 = [压缩伪消息] + [firstKeptEntryId … 末尾] 的消息
· ★ 指针找不到 ⇒ 从 0 开始（宁可多显示也不丢内容 ✓）
```

**验收**（`check-session-file.mjs` 加了 5 条不变量）：

```
那个文件里有【2 个】compaction 事件 ✗ 裁剪后只剩 1 个 ✓（12 项全通过）
```

```

**实时路径**：`entry_appended` 里 `entry.type === "compaction"` ⇒ `reset` + 重放 ✓

## 三、★★ 切换会话不再启动 pi（补上 B43 漏掉的路径）

**用户指出的问题**：

> "我对会话说的一切操作，在发送第一句话之前，pi 都不应该启动。
>  因为渲染所需的数据都从数据文件里取啊。"

**当时的代码**：

```ts
await pi.sendRaw({ type: "switch_session", sessionPath });  // ★ RPC ⇒ 把 pi 拉起来了
chatState.reset();
await deps.replay(sessionPath);                             // ★ 这一步才是零进程的
```

**用户的心智模型（关键）**：

> "切换会话的本质只不过是一种**参数** —— 跟 cwd 一样。
>  你启动的时候那个会话参数，难道不是动态的？"

⇒ **修正**：

```
点会话列表：只改 pendingSession（纯变量 ✗ 不碰 pi）+ 读文件渲染 ✓
发 prompt  ：applyPendingSession()
                同 cwd  → switch_session
                跨 cwd  → pi.setCwd + reload（reload 自己判断"没在跑就不重启"✓）
```

**连带修的**：
- 压缩重放要"读哪个文件"⇒ ★ 用**渲染入口记下的** `renderedFile`（不是问 pi ✓）
- 顶栏 cwd 显示**目标会话的** cwd（原来显示 pi 的旧值 ✗）

## 四、完整历史面板（独立 webview）

**入口**：会话面板右键 ⇒「全量渲染查看（带已压缩历史）」

```mermaid
flowchart LR
    R["会话面板右键"] --> H["session-host 路由"]
    H --> M["main.ts<br/>readSessionFile(path, raw:true)"]
    M --> T["★ 临时 ChatState 实例<br/>离线算 snapshot"]
    T --> P["HistoryPanel.post(fullHistory)"]
    P --> W["history.html<br/>★ 加载 media/out/history.js"]
    W --> A["apply.ts 的 replaySnapshot<br/>（聊天页同一条渲染路径）"]
```

**四个复用的设计**：

```
① 渲染器：history.js【就是聊天页那套】⇒ 2.9MB（与 chat.js 同量级 ✓）
   ★ 前端入口只有 30 行：握手 + 收快照 ⇒ 转给 replaySnapshot
② html-loader 按同名解析 ⇒ history.html 自动加载 out/history.js（零新机制 ✓）
③ 离线算快照：new ChatState() 临时实例 ⇒ ★ 不污染当前会话的权威状态 ✓
④ raw 模式：readSessionFile(path, {raw:true}) ⇒ 不裁剪压缩 ⇒ 全部历史都在 ✓
```

**history.html 是 chat.html 的删减版**：只留 `#messages` + 一排 `hidden` 的占位
（给 `dom.ts` 的 `needEl` 一个交代 ✗ 不依赖 CSS ⇒ 不会闪 ✓）

## 五、这一轮修的 bug（都是用户实测报的）

### 5.1 编辑器跳转（压缩摘要）

| 现象 | 根因 | 修 |
|---|---|---|
| Ctrl+Shift+V 渲染失效 | 只读编辑器限制 | 点击直接走 `markdown.showPreview` |
| 每次弹【新组】 | `showPreviewToSide` | 改 `showPreview`（当前组 ✓）|
| 重复点击重复弹 | `registerVirtualDoc` 每次都 `seq++` ⇒ 新 URI | 加 **key** 复用同一 URI ✓ |

顺带给 `virtual-docs.ts` 加了 `onDidChange`（内容变了 ⇒ 已打开的编辑器刷新 ✓）

### 5.2 渲染性能（卡）

```ts
// code-fit.ts 原来：每个代码块 2 次强制同步布局
for (const block of ...) {
    block.style.removeProperty("--code-scale");
    void pre.offsetWidth;          // ★ 强制布局 #1
    const avail = pre.clientWidth;
    const need  = pre.scrollWidth; // ★ 又一次
}
// 更糟：refold() 里每个工具块都调一次 ⇒ 全量重放 N 次

// 现在：① 全部复位（写）② 强制布局【1 次】③ 全部测量（读）④ 统一写回（写）
//      + 批量模式：replaySnapshot 期间抑制 per-block 的 fit ✗ 末尾统一算一次
```

**实测结果**：`建DOM 170ms · 封尾(marked) 6ms · 代码块宽度 0ms` ✓
（"好几秒"在宿主侧读文件 ✗ 不在渲染 ✗ 用户确认"样本大 ✗ 性能优化不是现在该做的"✓）

### 5.3 闪烁（左上角）

```
第一次报：完整历史面板左上角闪方框
  → 我的隐藏占位用 CSS 类 ✗ CSS 加载前 position:absolute 元素坍缩到左上角
  → 改用 HTML 的 hidden 属性 ✓

第二次报：主区也闪，而且"像是别人的样式"
  → ★ 那是 【mermaid 的错误图】！
     消息里有个语法错的 ```mermaid ⇒ mermaid.render() 失败时
     会把错误图（"mermaid version 12.1.0" + "Parse error on line 8" + 炸弹图标）
     插进它临时建的容器，且某些路径下【不清理】⇒ 留在 document 里叠在正文上 ✓
  → 修：① mermaid.initialize({ suppressErrorRendering: true })（官方选项 ✓）
        ② 失败 ⇒ ★ 静默回退成普通代码块（用户明确要求 ✓）不插任何提示 ✓
        ③ 清掉 mermaid 可能留在 body 上的临时容器 ✓
```

**还有一处"闪"没解决**（用户同意搁置）：
> "左上角还是有东西在闪 ✗ 慢慢来吧 ✗ 有影响或者拿到具体证据再看"

### 5.4 收缩规则没接上

```
根因：ui.defaultToolCollapsed 是 input.ts 设置的
    而历史面板【不加载聊天页入口】⇒ 一直是 false ⇒ 收不起来
修：① 宿主 ready 时推 styleVars ⇒ 面板调 applyStyleVars（★ 同一套规则）
    ② ui.historyMode 标志 ⇒ 历史面板默认【全收起】（消息成百上千条 ✓）
    ③ toolFold 规则照吃（同一个函数 ✗ 零重复逻辑 ✓）
```

### 5.5 切走再切回要重等

```
根因：webview 默认 retainContextWhenHidden=false ⇒ 一隐藏就丢 DOM
     切回来重新加载 2.9MB 脚本 + 重渲染上百条消息
修：retainContextWhenHidden: true（代价：后台占内存 ✗ 它就是个只读档案 ✓）
```

### 5.6 守门脚本再次立功

```
check-style-vars 的"断点 C"两次抓到：CSS 消费了没定义的变量
  · --pi-bg-compaction / --pi-rail-color-compaction / --pi-compaction-max-height
  · --pi-history-banner-h
⇒ 都补进 base.css 的 :root（★ 规则：变量必须在 CSS 里显式定义 ✗ fallback 不算 ✓）
```
