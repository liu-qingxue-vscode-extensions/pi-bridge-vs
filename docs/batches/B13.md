### ② ★ 重大发现：官方 `RpcClient` 的出口不够用

**起因**：做回复桥时需要给 pi 发 `extension_ui_response`，于是去翻官方客户端 ✗

**翻出来三件事**：

```
① send() 是 private ✗
   （源码里是 public，但 .d.ts 标了 private → 类型上不可用）

② ★ 更关键：pi 对 extension_ui_response 【不返回执】✗
   源码：handleInputLine 收到它 → 直接 resolve pending，不 output(response)
   → 就算调 send()，也会一直挂到 30s 超时 ✗
   → 这是【协议语义】问题，不是客户端 bug ✓

③ 我自己早就在绕私有字段了 ⚠
   attachStderr：读 this.process（官方的拉取式 getStderr 拿不到实时 ✗）
   （马上还要再加一个 replyExtensionUi：读 this.process.stdin）
```

**用户的判断**（很准 ✓）：
> "它以扩展性为名封装了个客户端，一开始引诱我去用，我还以为它原生呢。
> **它好歹得有个兜底接口啊** —— 没兜底接口，那就不叫服务性封装 ✗
> 服务性封装肯定要给兜底出口；搞得只能"有线封装"、还搞 private，那就有病 ✗"

### ③ ★ 决策：自持传输层（复制官方核心并改造）

**关键区分（决定怎么复制）**：
```
【协议契约层】RpcCommand / RpcResponse / JsonAgentSessionEvent / RpcExtensionUIResponse
              = pi 的协议定义 → ★ 继续 import 官方 ✓（契约不该复制 ✗，pi 变它本来就该变 ✓）

【传输实现层】spawn / stdin 读写 / stdout 逐行解析 / pending 表 / 超时
              = Node child_process 的搬运 → ★ 自己写 ✓
                不依赖 pi 版本 ✓ 而且【能开出口】✓
```

**要做的**：
```
1. 新建 src/pi/rpc-client.ts —— 从官方复制核心（约 100~150 行）
2. ★ 开出口（消灭私有依赖）：
     · send() 公开 ✓
     · 提供子进程访问（stdin 写 / stderr 事件）✓
3. PiClient 改用它（其余代码不动 ✓）
```

**收益 / 代价**（用户点的很明白 ✓）：
```
收益：完全掌控 ✓ 不再依赖私有字段 ✓ 需要什么出口就加什么 ✓
代价：pi 协议变了要自己跟 ✗（低频事件，可接受 ✓）
      以及约 150 行自有代码的维护
★ 时机理由：现在项目小，改造成本最低 ✓（"搞大了再改成本更高"✓）
```
