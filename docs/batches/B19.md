### ① 实测定下的四条事实（`scripts/probe-clone-fork.mjs` ✓）

```
【clone】无参数 ✓
  返回 {"cancelled": false}              ← ★ 没有别的字段 ✗
  → 新文件 2026-10-03T09-20-46-249Z_….jsonl  ← ★ 全新文件 ✓ 原会话不动 ✓
  → 消息数 = 原会话全部（6 ✓）

【get_fork_messages】
  → 只含【用户消息】✓ 每条带 { entryId, text }
  → test 会话 2 条 ✓（对应 2 轮 ✓）

【fork(第 2 条)】
  返回 {"text": "我在测试…", "cancelled": false}   ← ★ 会回传那条的文本 ✓
  → 新文件 ✓ 消息数 4
     ★ = 只【截到那条之前】✗（不含那条本身 ✓ 也不含它的回答 ✓）

【fork(第 1 条)】

```

**四条结论** ✓：
```
① clone = 无参数，整会话复制 → 新文件 ✓
② fork(entryId) = 截到【那条用户消息之前】✓ → 新文件 ✓
③ ★ 两者【都会自动切换】✓（不用再 switch ✓ 源码 rebindSession ✓ 实测确认 ✓）
④ ★ 两者【都新建文件】✗ 原会话毫发无损 ✓（所以不需要二次确认 ✓ 很安全 ✓）

★ 附加：fork 之后【旧 entryId 失效】✗ → 不能缓存列表 ✓ 每次现取 ✓
```

### ② ★ 关键调研：turn 在哪里？（用户的担心成真了 ✓）

用户问：**"turn 是文件里的内容吗？文件里如果没有 turn，那不就完蛋了？"** ✓

**查证** ✓：
```
【会话文件 .jsonl 里的 type 分布】
  3 custom / 2 custom_message / 4 message
  1 model_change / 1 session / 1 session_info / 1 thinking_level_change
  ★ 含 "turn" 字样的行：0 行 ← ★★ 文件里【根本没有 turn】✗

【但文件里有 id + parentId ✗】：
  {"type":"message","id":"130c4714","parentId":"af627b06","message":{…}}
  {"type":"message","id":"3bb8c3ba","parentId":"130c4714",…}
  {"type":"message","id":"fde40ca3","parentId":"8ddd99cd",…}

★★ 对照：get_fork_messages 的 entryId = 130c4714 / fde40ca3 ✓✓✓
   → ★ 文件里的 id 【就是】fork 需要的 entryId ✓ 完全对上 ✓
```

**四条结论** ✓：
```
① turn 【不是文件里的东西】✗ 是运行时临时概念 ✓
② 文件里【有 id / parentId】✓ 但 get_messages 【不返回它们】✗
③ ★ 文件的 id == fork 的 entryId ✓（实测对上 ✓）
④ ★ turn 的边界 = 用户消息的位置 ✓（用户一句话点破的 ✓）
→ 所以【能推出来】✓ 不需要文件里有 turn ✓ 也不需要消费 turn_* ✓
```

### ③ ★ 那把刀：按钮挂哪儿、传什么 ID（用户定的 ✓）

**用户的比喻** ✓：
> "那个按钮那个位置就像一把刀一样切一刀，懂了吧？前面的保留，变成复合内容"✓

**于是语义链** ✓：
```
刀挂在【某个 AI 组（turn）的末尾气泡】下面 ✓
  → 要保留"到它为止"✓
  → fork 的实际语义是"截到某条【用户消息】之前"✗
  → ★ 所以必须传【它后面那条用户消息】的 entryId ✓

[用户A][AI-A]  [用户B][AI-B]  [用户C][AI-C]
                      ↑ 刀在这
              fork(用户C 的 entryId) → 保留到 AI-B 为止 ✓
                                        ★ 含 AI-B ✓

★ 最后一组（AI-C）：它后面【没有用户消息】✗
  → 没有锚点 → ★ 不加按钮 ✓（用户："这正好，这没有问题"✓）
★ 这也正好解释了后端的限制：不能从当前轮次 fork 出去 ✓（不是 bug，是语义必然 ✓）
```

### ④ ★ 不用消费 turn_*：从气泡序列就能推（实现关键 ✓）

```
★ AI 组 = 【两个 user 气泡之间的】连续非 user 气泡 ✓
★ 组尾   = 该组最后见到的那个非 user 气泡 ✓（后面的覆盖前面的 ✓）

→ 扫一遍气泡数组即可 ✓ 实时 / 重放【同一套逻辑】✓ 幂等 ✓
```

**动态回填** ✓（这是"动态"的正解 ✓）：
```
实时流里：渲染 AI-B 时【下一轮还没来】✗ → 不知道 entryId ✓
→ ★ 等用户C 到达时再回头补 AI-B 的按钮 ✓
   （每次 patch 后都跑一次 refreshForkButtons ✓ 幂等 ✓ 自然就把上一组补上了 ✓）

重放历史：全部气泡一次到位 ✓ → 一次算完 ✓
```
