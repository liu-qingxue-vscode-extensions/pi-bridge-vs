### ⑥ ★★ 会话列表：两级 I/O 模型（本轮的核心设计）

**问题**：列表要两类信息，成本差得远 ✗
```
【第一类：有哪些会话】
  readdir 一次全拿到 ✓ 文件名里还有时间戳 + id ✓
  → 便宜到可以每次打开都扫 ✓

【第二类：会话名字】
  只能【读文件末尾】✗（session_info 是每轮追加的 ✓）
  → 80 个文件 = 240 次 syscall ✗ 不能每次扫 ✓
```

**用户定的两级模型** ✓：
```
【第一级 条目层 —— 自动 ✓】
  打开面板 → readdir → 与缓存比对差异 → 增删条目
  ★ 零内容 IO ✓
  cwd 的特殊性：目录名是【有损转义】✗（/ 换成 - → my-project 和 my/project 撞车 ✗）
    → 只能读文件首行拿 cwd ✓ 但【一个目录只读 1 个文件】（同目录 cwd 必然相同 ✓）
    → 且只对【新目录】读 ✓ 一次性 ✓ 之后恒为 0 ✓

【第二级 内容层 —— 手动 ✓】
  点 ⟳ 刷新 → 才读文件补名字 + 检异常 ✓
  ★ 维护边界 = 用户点刷新的那一刻 ✓
    （文件内部改了但没刷新 → 显示旧名字 ✓ 用户明确接受 ✓）

【存储】统一一个 JSON（globalState ✓）
  { cwdMap: 目录名→cwd,  files: path→{name, broken} }
```

**为什么用 globalState 而不是自己写文件** ✓：VS Code 会落盘成 JSON ✓ 省掉"读写+并发+损坏处理"✗

**键大小**：读头部 4KB（拿 cwd / 验完整性）+ 读尾部 16KB（拿名字）✓
> jsonl 行不定长 ✗ → 无法"跳到第 N 行" → 只能 seek 到末尾读一段再按 \n 切 ✓
> 可能切到行中间 → 那行 JSON 解析失败 → 跳过 ✓ 无害 ✓
> ★ 代价对比：读 16KB vs 读 11MB（实测最大文件）→ 差 700 倍 ✓
