## 一、★ 先聊清楚：是框架的罪吗？

### ① 用户的自我怀疑

```
“我不懂前端，菜就是原罪呀。前端我们做的很辛苦 ✗
 我感觉框架可能是有问题 ✗ 导致我们这么辛苦 ✓
 按理来说，我们应该拆分前端的效果 ✗ 把效果给统一实现 ✗
 然后就可以在往后的迭代里面复用 ✗ 而不用每次都要单独每一样都要实现 ✓
 ……你认为我们现在的开发模式有问题吗？”
```

### ② 结论：有一部分是，但主要不是

```
★ 前端的辛苦来自【三个真实复杂度】✗ 不是抽象没做好 ✓
   ① 流式渲染 ✗ AI 前端最经典的难题（业界都在攻坚 ✓）
   ② DOM 命令式操作 ✗ 每次改状态都要手动同步 ✓
   ③ 高频事件 + 全量重绘的冲突 ✓（反复踩 ✓）

★★ 但确实有一部分是【模式造成的】✗：
   · 每个功能都"从零串一遍"✗（顶栏 / 面板 / 菜单 / 输入区各写各的 ✓）
   · 没有【统一的组件概念】✗ 只有"函数 + 直接操作 DOM" ✓
   · 副作用散落 ✗ 谁在什么时候重绘 / 谁调 syncPadding ✗ 靠人记 ✓

★★★ ★ 数据佐证（B25~B29 的 bug 统计 ✗）：
   渲染层 ≈ 90%  ·  逻辑层 ≈ 10%
   ⇒ 逻辑层（我们抽出来的纯状态 ✓）明显更干净 ✓
   ⇒ 因为它没有 DOM 可以乱来 ✓✓✓
```

### ③ 用户提出的一个构想（★ 值得记下来 ✓）

```
“我手写写出 input output 的终端程序 ✗ 来模拟前端行为 ✗
 然后你直接读着这样的 input output 来转换成 UI 框架 ✓
 这样的话起码这个框架本身是正确的 ✗ 至于 UI 怎么实现那都是小问题 ✓”
```

★ 我的评估 ✗：**方向对**（这正是 Elm Architecture / Redux / MVI 的思想 ✓）**但有两个边界** ✓

```
✅ 能转的：状态机 · 数据流 · 交互规则（纯函数 ✓）
❌ 不能转的：交互词汇表 ✗ TUI 和 GUI 根本不同 ✓

   同一功能        TUI              GUI
   ──────────     ──────────       ──────────
   折叠气泡        重新打印一段       display:none
   滚到底部        继续输出           scrollTop = scrollHeight
   复制代码        终端自带选择       按钮 + clipboard API
   悬停 / 右键     ✗ 不存在          title / contextmenu
   拖拽选区        ✗ 不存在          selection API
   输入框光标      终端行内光标       textarea.selectionStart

⇒ ★ 空间结构 / 控件选择 / 反馈方式 ✗ 这些是【设计决策】✗ 转译不了 ✓
```

★ 更直接的替代 ✗：**不必写 TUI** ✗ 直接把那个纯函数边界定死 ✓
```ts
function onKey(s: UiState, key: Key): { state: UiState; effects: Effect[] }
type Effect = { kind: "focusInput" } | { kind: "scrollTo"; target: string } | …
```
· TUI 版 = 实现 Effect 的"终端语义" ✓
· GUI 版 = 实现 Effect 的"DOM 语义" ✓
· ★ 两边共用同一份 `onKey` ✗ 不可能出现"逻辑两处不一致" ✓

★★ **决定** ✗：**现在不重构** ✓ 剩下的活只有三件 ✗ 重构成本极高 ✓
但把上面的判断写进 `docs/UI-GUIDE.md` ✗ 供后续参考 ✓

## 二、★ 拆分 main.ts（2032 → 1729）

### ④ 拆分原则

```
★ 按【功能域】拆 ✗ 不按行数 ✓
★★ 优先搬【函数体里没有引用闭包变量】的 ✗ 这类零风险 ✓
   （闭包变量 = pi / chatView / chatPanel / context / cwd / pushHint … 系列 ✓）
```

### ⑤ 搬运方式（★ 关键 ✗ 用脚本按行切 ✗ 不手抄 ✓）

```
① Python 按【函数名 + 4 空格缩进】定位起止 ✗
   ★ 坑：大括号计数会被【类型注解里的 {}】骗到 ✓
     （`list: { provider: string }[]` ✗ 导致 sortCatalog 只切出 2 行 ✓）
     ⇒ 改用"第一个顶格 4 空格的 `}`"判定 ✓
② 从后往前删 ✗ 保持行号有效 ✓
③ ★ 新文件里的函数要【整体去 4 空格缩进】✗
   （从 activate 内部切出来的都带缩进 ✗ 不去就是嵌套函数 ✗ 不是模块成员 ✓）
④ 补 export + import ✓
```

★ 这套流程走下来 ✗ **TypeScript 编译器全程兜底** ✗
（少 import / 名字没 export / 类型不匹配 ✗ 全部立刻报错 ✓）
⇒ ★ 所以"旁边建目录再搬"和"直接搬"在 TS 里是同一件事 ✓
真正要防的是**行为悄悄变了** ✗ 那个只能靠小步 + 看 diff ✓
